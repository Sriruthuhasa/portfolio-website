Kubernetes on AWS: What No One Tells You When You're Starting Out

At Axis Bank, we needed to deploy AI-driven testing tools into client environments — isolated, reproducible, and scalable. The answer was Kubernetes on AWS. What followed was three months of configuration headaches, namespace confusion, and resource limit disasters. Here's what I wish someone had told me.

Lesson 1: Namespaces Are Not Optional

I started deploying everything into the default namespace. This works fine until it doesn't — you lose visibility, resource isolation breaks down, and RBAC becomes a nightmare. Create namespaces early, name them consistently (we used testing-{env}), and treat them as first-class citizens.

Lesson 2: Always Set Resource Limits

Our AI testing tools were memory-hungry. Without limits, one misbehaving pod would starve the entire node. This is the config pattern that saved us:

resources:
  requests:
    memory: "512Mi"
    cpu: "250m"
  limits:
    memory: "1Gi"
    cpu: "500m"

Start conservative, monitor with kubectl top pods, and adjust. Never skip this.

Lesson 3: Health Checks Are Not Optional Either

Without readiness and liveness probes, Kubernetes will send traffic to pods that aren't ready, and won't restart pods that are silently broken. Add both from day one — even a simple HTTP check is infinitely better than nothing.

Lesson 4: AWS EKS IAM Is Confusing But Critical

The IRSA (IAM Roles for Service Accounts) model feels over-engineered at first. Stick with it. It gives your pods fine-grained AWS permissions without passing access keys around. The setup takes an hour; the security benefit is permanent.

What I'd Tell Past Me

Don't rush to Kubernetes if Docker Compose gets you where you need to go. K8s pays off at scale — multi-service, multi-environment, team-sized deployments. For a single service, it's overhead. We genuinely needed it at Axis Bank because we were deploying across multiple client-isolated environments with different configurations. If you don't have that problem yet, wait.

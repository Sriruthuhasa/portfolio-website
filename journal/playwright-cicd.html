Testing CI/CD Playwright

April 2025 · 8 min read

Scaling Playwright Tests Across a CI/CD Pipeline at Axis Bank

When I joined the Axis Bank team as a Software Test Engineer, the QA process was a combination of manual testing and a handful of brittle Selenium scripts. Deployments took hours. Regressions slipped through. We needed a proper automated testing strategy — and we needed it yesterday.

Here's what we built, what broke, and what we'd do differently.

Why Playwright Over Selenium

The team had historical baggage with Selenium — flaky waits, driver version mismatches, slow parallel execution. Playwright solved most of these out of the box: auto-waiting, built-in parallelism, TypeScript-first API, and an incredibly fast execution engine built on Chrome DevTools Protocol.

The Architecture

We structured our test suite into three layers:

1. Unit-level component tests — fast, isolated, running on every push. 2. Integration flows — user journeys across the banking portal, running on pull requests. 3. Full E2E smoke suite — running only on merges to main, with a dedicated test environment.

Sample test structure

// tests/auth/login.spec.ts
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test.describe('Login Flow', () => {
  test('should authenticate with valid credentials', async ({ page }) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await loginPage.login('testuser@bank.com', process.env.TEST_PASSWORD!);
    await expect(page).toHaveURL('/dashboard');
    await expect(page.getByTestId('welcome-banner')).toBeVisible();
  });
});

The CI/CD Integration

We ran Playwright inside Docker containers on Azure DevOps pipelines. The biggest challenge was flakiness from network timeouts in the containerized environment. We solved it with retry logic at the pipeline level and by setting conservative timeouts in playwright.config.ts.

Results

After 3 months: deployment confidence went up, manual QA time dropped by ~60%, and we caught 4 production-level regressions before they hit users. The test suite now runs in under 8 minutes on pull requests — fast enough to not block anyone.

The lesson: start with the most-used user flows, not the edge cases. Coverage on critical paths is worth ten times more than covering rare scenarios that nobody tests manually either.
